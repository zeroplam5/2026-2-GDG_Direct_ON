# 베이스라인 결과 보고서 (2026-11-18, 사전 연습용)

> **갱신 (2026-11-18 2차)**: `.env`에 OpenAI 키가 추가되어 **실제 LLM(gpt-4.1, gpt-4.1-mini)으로 측정했습니다.** 결과는 §3.4에 있습니다.
> 아래 1차 서술 중 "실제 LLM 미실행" 부분은 Upstage 키 기준입니다.

> **(1차) 먼저 밝혀 둘 점.** 이 PC에서 사용할 수 있는 LLM이 없어 **실제 LLM으로는 한 번도 실행하지 못했습니다.**
> `UPSTAGE_API_KEY`는 설정되어 있지만 API가 `403 API key suspended due to insufficient credit`을 반환했습니다.
> 따라서 아래 결과는 모두 **실제 STT(faster-whisper, GPU)와 실제 TTS(Windows SAPI)** 에 **스크립트형 대체 LLM(정규식 규칙, AI 아님)** 을 연결해 얻었습니다.
> 응대 품질, 즉 LLM의 판단·자연스러움·인계 판단은 **측정되지 않았습니다.** 속도 수치에도 실제 LLM의 지연은 들어 있지 않습니다.
> 측정에 쓴 측정기와 점수표는 스타터킷의 데모용이며, 공식 점수가 아닙니다.

**발견한 스타터킷 이상** (운영진 확인 필요, 어느 쪽이 의도인지는 판단하지 않음):
1. **데모 음성 3개가 README 설명과 다릅니다.** README에는 "영어 합성음"이라고 되어 있지만, STT 결과 세 파일 모두 한국어였습니다(언어 감지 확률 0.98 이상). 내용도 `demo_cases.jsonl`의 `customer_utterance`와 다릅니다.
   - DEMO1.wav (8.3s): "카드 사용이 어렵네요. 임서재 010…" / 케이스 텍스트: "Hello, what time do you open?"
   - DEMO2.wav (3.65s): "효과적인 복용 방법은 무엇입니까?" / 케이스 텍스트: "My order number is demo one zero zero one…"
   - DEMO3.wav (9.3s): "택배 상자가 없어서… 반품이라고 접어서 내놓으면 되겠죠?" / 케이스 텍스트: "Please call me back tomorrow."
2. **`meta.json`의 `speech_end`가 실제 음성과 맞지 않습니다.** DEMO2는 파일 길이가 3.65s인데 `speech_end`는 5.337s입니다. DEMO1·DEMO3은 `speech_end` 뒤에도 큰 음성이 5~6초 이어집니다.
   그래서 위의 DEMO2 "끼어듦"과 DEMO1·3의 5~7초 지연은 **서버 성능이 아니라 메타데이터 불일치에서 생긴 값**입니다. 이 3개 파일로 잰 속도는 의미가 없습니다.
3. Windows 기본 인코딩(cp949) 환경에서 `run_eval.py`는 `open()`에 인코딩을 지정하지 않습니다. 한글이 든 UTF-8 케이스 파일을 쓰려면 `PYTHONUTF8=1`이 필요합니다. 원본은 고치지 않았습니다.
4. 원본 예시 서버의 판정 규칙(RMS 500 이상, 무음 800ms)을 팀 음성에 적용하면 24회 중 15회 끼어들었습니다(§3).

## 2. 구성도와 파일별 역할

```
측정기(run_eval)                                  상담원 서버 (team/agent, 연결마다 Session 1개)
 ─ session.start(JSON) ─────────────▶ Session._read_start ── ToolsClient(tools_url, X-Session-Id) ─ GET /tools ─▶ 모의 서버
 ─ PCM 20ms × N (발화 뒤 무음 계속) ─▶ FrameAssembler → Endpointer(VAD)
                                         │ 무음 ≥400ms: STT 미리 시작 (부작용 없음, 말이 이어지면 버림)
                                         │ 확정: (무음 ≥1100ms 그리고 문장이 완결돼 보임) 또는 무음 ≥1800ms
                                         ▼
                                       STT 결과 → Dialog(LLM 스트리밍) ─ 함수 필요 ─▶ ToolsClient.call ─ POST /tools/{name} ─▶ 모의 서버
                                         │            ◀── 결과(JSON)를 tool 메시지로 다시 전달 ──┘
                                         ▼ 문장 단위
                                       TTS(SAPI) → PCM 프레임
 ◀─ PCM, agent.transcript ──────────────┘
 ◀─ {"type":"turn.end"} (항상 마지막, finally에서 전송)
```
파일별 역할은 [README.md](../../../README.md#파일-구성)에 정리했습니다.
세션 사이에 공유하는 것은 읽기 전용 자원(STT 모델, TTS 스레드 풀, LLM 클라이언트, HTTP 연결 풀)뿐입니다. 오디오 버퍼, 대화 이력, 함수 클라이언트, 응답 상태는 모두 Session 객체 안에 있습니다.

### 3.4 실제 LLM(OpenAI) 측정 — 2차

- 구성: 실제 STT와 실제 TTS + OpenAI Chat Completions 스트리밍
- 원자료: `team/runs/bench*_gpt-4.1*/`

## 4. API 키나 환경이 없어 검증하지 못한 항목
- **실제 LLM 전체**: 함수 호출 판단 정확도, 필수 정보 확인 질문, 정정 처리, 인계 판단, 환각 여부, 응답 지연(클라우드 왕복 포함). 키는 존재하지만 크레딧 부족으로 정지 상태입니다.
  로컬 LLM 런타임(Ollama 등)은 설치되어 있지 않아 설치하지 않았습니다.
- 실제 사람 목소리와 전화망 음질에서의 STT 정확도와 VAD 동작. 연습 음성은 깨끗한 합성음입니다.
- `output_pacing=realtime`(실시간 속도 송신), 다른 샘플레이트 입력의 리샘플링, 한 연결 안에서의 여러 턴(측정기는 1턴 후 종료).
- 공식 평가 서버와 함수 중계 환경, Linux/macOS 실행(SAPI TTS는 Windows 전용).

## 5. 현재 한계와 알려진 위험
1. **조기 응답과 지연은 맞바꾸는 관계입니다.** 완결돼 보이는 문장 뒤 1.1s 이상 쉬면 끼어듭니다(K05). 무음만으로 1.5s를 기다리면 끼어듦은 0이지만 첫 소리가 약 0.4s 늦어집니다.
   문장 완결 추정은 단순한 한국어 어미 규칙이며, STT가 미완성 문장에도 마침표를 찍는 경우가 있습니다.
2. 반이중 방식입니다. 응답하는 동안 들어오는 고객 음성은 버리므로 말 끊기(barge-in)를 지원하지 않습니다.
3. LLM이 함수 호출 전에 문장을 내면 그 문장은 바로 읽힙니다. 프롬프트로 사실 언급을 금지했지만, 코드 수준의 근거 검증은 없습니다.
4. 함수 호출이 시간 초과로 취소돼도 서버 쪽에서는 실행됐을 수 있습니다. 접수류 함수의 중복이나 미확인 상태를 처리하는 규칙이 없습니다.
5. 실제 LLM을 쓰면 **고객 발화 텍스트, 발신자 정보, 이전 이력이 외부 LLM 제공사로 전송됩니다.** 대회 자료를 외부로 보내도 되는지는 **미확정**입니다.
   STT와 TTS는 로컬에서 처리합니다. 에이전트는 수신 음성을 저장하지 않습니다. 측정기가 저장하는 `agent_audio`는 상담원 출력 음성입니다.
6. 기록에는 기본적으로 시간 값만 남습니다. `AGENT_LOG_TEXT=1`이면 인식 텍스트와 응답도 로컬 파일에 남습니다. 이 저장소의 `team/runs/*metrics*.jsonl`에는 측정 중 켰던 텍스트가 남아 있습니다(연습 음성과 스타터킷 가상 데이터).
7. SAPI 음성은 기계음이고 Windows 전용입니다. faster-whisper `large-v3-turbo`는 GPU가 필요합니다(CPU에서는 small 모델로 2~3s가 걸렸습니다).
8. 모의 서버의 매칭 규칙(공백·하이픈·대소문자 무시), not_found 문구, 미정의 함수 호출 기록 방식은 **예제용 선택**입니다.

## 7. 속도·정확성·자연스러움 사이에서 내린 선택과 이유
- **발화 종료 1100/1800ms**: 측정 결과 800ms 이하는 문장 사이 쉼에서 끼어듦이 많았습니다(15/24). 끼어듦은 데모 점수표에서 속도 0점이고, 상담 경험에도 가장 나쁩니다. 그래서 첫 소리를 약 0.3~0.4s 늦추는 대신 끼어듦을 3/24로 줄였습니다.
  끼어듦을 0으로 만들려면 무음만으로 1.5s 이상 기다려야 합니다. 공식 판정 기준을 보고 다시 정합니다.
- **STT만 미리 실행하고 LLM과 함수는 확정 뒤에 시작**: STT는 부작용이 없어 결과를 버려도 됩니다. 함수 호출은 기록되므로 고객이 말을 이어 가면 잘못된 호출이 남습니다. 측정 결과 확정 뒤 STT 대기는 0ms였습니다.
- **로컬 STT와 TTS**: 지연이 짧고(STT p50 230ms, TTS 18ms), 음성 데이터가 외부로 나가지 않습니다. 대신 TTS 음질이 낮고 Windows에서만 동작합니다. 공급자는 설정으로 바꿀 수 있습니다.
- **LLM은 OpenAI 호환 인터페이스 하나로 구현**: 대회에서 허용하는 모델이 정해지지 않았으므로 URL과 모델명만 바꾸면 되게 했습니다.
- **채움말을 쓰지 않음**: 프롬프트에서 습관적인 "네, 알겠습니다"를 금지했습니다. 함수를 호출하기 전 안내 멘트 같은 방법도 기본적으로 쓰지 않습니다. 속도 점수만 위한 장치는 넣지 않았습니다.
- **함수 결과를 엄격히 다룸**: 정의되지 않은 함수와 인자 오류는 로컬에서 차단합니다. 오류와 시간 초과는 `status:error`로 바꾸고, `status`가 없는 응답은 `unknown`으로 표시합니다. 이렇게 해서 모델이 성공으로 오인할 여지를 줄였습니다.
- **`turn.end`는 항상 전송**: 오류나 시간 초과 때도 미리 합성해 둔 대체 문구를 말한 뒤 `turn.end`를 보냅니다(20s 예산, 측정기 제한은 25s).
