# 말 끝 판단 비용표: 끼어듦 vs 기다림

2026-11-21 · 정리 조여정 · 브랜치 `feature/eou-cost` · 연습 자료 기준이며 공식 점수가 아닙니다.

## 공식 연습 음성 기준 (11/21, 이 문서의 결론)
공식 자료(`directon-2026-voice-cs`)의 연습 음성 80개로 다시 쟀습니다. 시험 문항도 같은 방식(음성합성, 목소리·말투 8가지)으로 만든다고 공식 README에 적혀 있습니다. 공식 음성·문항은 저장소에 넣지 않았고 숫자만 옮겼습니다.

### 1) 공식 음성의 말 중간 쉼 (음량으로 측정)
| 항목 | 값 |
|---|---|
| 문항별 가장 긴 쉼 | 중앙 0.44초, 상위 10% 0.66초, 최대 1.82초 |
| 0.8초 넘게 쉬는 문항 | **3 / 80** |
| 1.0초 넘게 쉬는 문항 | **1 / 80** (1.82초) |
| `meta.json` 말 끝 vs 음량으로 잰 말 끝 | 차이 중앙 0.02초, 최대 0.12초 (믿을 만함) |

팀이 만든 연습 음성(1.2~1.5초 쉼을 일부러 넣음)보다 쉼이 훨씬 짧습니다. 지금 기본값(완결 1.1초 / 최대 1.8초)은 팀 음성에 맞춘 값입니다.

### 2) 제출 버전 상담 서버 × 공식 측정기 (80문항, 동시 4)
- 서버: `feature/submission` 코드, 대체물 provider(STT는 문항의 실제 손님 문장을 돌려주는 가짜, LLM 스크립트, TTS 신호음). 말 끝 판단 코드는 실제와 같음
- 측정기: 공식 `eval/run_eval.py` 그대로
- 점수: **사이트 속도 공식** (첫 소리 표, 함수 문항은 조회 뒤 답 표와 평균). 조회 뒤 답은 2.5초(100점 구간)로 가정
- 처리 시간 = 말 끝 판단 뒤 첫 소리까지(STT→LLM→TTS). 공식 모델로 아직 못 재서 1.0~2.5초로 가정

| 말 끝 규칙 | 끼어듦 | 말 끝 판단 p50 / p90 | 처리 1.0초 | 처리 1.5초 | 처리 2.0초 | 처리 2.5초 |
|---|---|---|---|---|---|---|
| **지금 기본값** (완결 1.1초 / 최대 1.8초) | 2/80 | 1.08 / **1.78초** | 81.1 | 74.0 | 66.9 | 57.3 |
| 완결 0.7초 / 최대 1.6초 | 4/80 | 0.68 / 1.58초 | 83.1 | 76.1 | 69.2 | 59.7 |
| 완결 0.6초 / 최대 2.0초 | 11/80 | 0.58 / 1.98초 | 74.9 | 68.6 | 62.3 | 53.4 |
| 침묵만 0.8초 | 5/80 | 0.78 / 0.78초 | 86.9 | 80.0 | 73.1 | 66.2 |
| **침묵만 1.0초** | 3/80 | 0.98 / 0.98초 | **89.2** | **82.2** | **75.2** | **68.2** |
| 침묵만 1.3초 | 1/80 | 1.28 / 1.28초 | 84.5 | 77.4 | 70.2 | 63.1 |
| 침묵만 1.5초 | 1/80 | 1.48 / 1.48초 | 84.5 | 77.4 | 70.2 | 63.1 |

(평균 속도 점수. 끼어든 문항은 0점.)

### 3) 읽는 법
- **침묵만 1.0초가 모든 처리 시간 가정에서 가장 높습니다.** 지금 기본값보다 속도 점수가 8~11점 높습니다(시스템 총점으로 약 2.4~3.3점, 행사 점수로 약 0.5~0.7점).
- 지금 기본값이 느린 이유: 공식 손님 말 중에는 번호로 끝나는 말처럼 "문장이 끝났는지 모름"으로 판정되는 경우가 많아서, 그때마다 최대 1.8초를 기다립니다(p90 1.78초).
- 대신 끼어듦이 2개 → 3개로 하나 늘어납니다. 끼어들면 그 문항 속도 0점이고 사용자 경험에도 나쁩니다.
- 1.3초·1.5초는 끼어듦이 1개(1.82초 쉼 문항)지만 모든 문항이 느려져 1.0초보다 낮습니다.
- 끼어든 문항: 기본값 P0071-05, P0130-01 / 침묵 1.0초 P0071-05, P0167-03, P0130-01

### 4) 믿을 만한 정도
- **침묵만 규칙들은 실제와 거의 같습니다.** STT를 쓰지 않고 공식 음성의 소리만 보고 판단합니다.
- **완결 규칙들(지금 기본값 포함)은 가짜 STT 영향이 있습니다.** 가짜 STT는 손님이 쉬는 중에도 전체 문장을 돌려주므로, 실제 STT보다 "완결"로 빨리 판정할 수 있습니다. 그래서 끼어듦은 실제보다 많게, 판단 시간은 실제와 다르게 나왔을 수 있습니다.
- 처리 시간과 조회 뒤 답 시간은 가정값입니다. 공식 키로 잰 값이 나오면 다시 계산합니다.

### 5) 적용 방법 (제출 형식 그대로)
코드를 바꾸지 않고 제출 압축의 `.env`에 두 줄을 넣으면 됩니다. `start_server.sh`가 같은 폴더의 `.env`를 읽습니다.
```
AGENT_SEMANTIC_EOU=0
AGENT_MAX_SILENCE_MS=1000
```
**기본값을 바꿀지는 팀이 정합니다.** 실제 키로 공식 연습 문항을 한 번 돌려 끼어듦과 첫 소리를 확인한 뒤 정하는 것을 제안합니다.

### 6) 다시 돌리기
```bash
# 공식 음성 80개 × 말 끝 설정 7개 (키 없음, 약 3분). --out 은 저장소 밖 폴더
python -m team.scripts.eou_sweep_official --official <공식 자료 폴더> --out <폴더>
# 비용표 (처리 시간·조회 뒤 답 가정값을 바꿔 가며)
python -m team.scripts.eou_cost_table --official-dir <폴더> --pipeline 1.0,1.5,2.0,2.5 --after-tool 2.5
```

## 왜 이 표를 만들었나
논문 정리 페이지의 FSTTM(Raux & Eskenazi, CMU Let's Go)은 말 끝을 고정 침묵 시간으로 정하지 말고, **끼어드는 비용과 기다리는 비용을 비교해** 정하라고 합니다.
이 대회는 두 비용이 같은 점수표에 있습니다.

| 경우 | 그 문항의 속도 점수 |
|---|---|
| 고객 말이 끝나기 전에 소리를 냄 (끼어듦) | **0점** |
| 첫 소리까지 1.5초 이하 / 2.0 / 2.5 / 3.0 / 3.5 / 4.0 / 5.0 / 6.0초 이하 | 100 / 90 / 80 / 70 / 60 / 50 / 30 / 10 |

첫 소리 = **말 끝 판단에 쓴 시간** + **판단 뒤 처리 시간(STT → LLM → 첫 TTS 소리)**.
말 끝 판단 시간은 측정값을 쓰고, 판단 뒤 처리 시간은 공식 모델로 아직 못 재서 **네 가지로 가정**했습니다.

| 가정한 처리 시간 | 근거 |
|---|---|
| 1.0초 | 빠른 경우 (예: 대기 멘트가 바로 나가는 경우) |
| 1.5초 | 중간 |
| 2.08초 | 실측: gpt-4.1 + OpenAI STT·TTS, 판단 뒤 첫 소리 p50 (`team/runs/fixed_gpt-4.1`) |
| 2.63초 | 같은 실측의 p90 |

## 읽는 법
1. **0.8초 이하 규칙은 어떤 경우에도 나쁩니다.** 끼어듦이 많아서, 빨리 답한 이득보다 0점이 더 큽니다.
2. **가장 좋은 규칙은 판단 뒤 처리 시간에 따라 바뀝니다.**
   - 처리가 빠르면(1.5초 이하) 끼어듦을 없애는 쪽(B의 침묵만 1.5초)이 이깁니다.
   - 처리가 느리면(2초 이상) 모든 문항이 0.4초씩 늦어지는 손해가 커져서, 지금 기본값이 이깁니다. A의 1.3초 → 1.5초도 같은 이유로 처리 2.63초에서 44.4 → 26.7로 떨어집니다.
3. **점수가 0.5초 단위 계단이라서**, 첫 소리가 계단 경계(2.0 / 2.5 / 3.0 / 3.5초) 바로 위에 걸리는지가 크게 작용합니다. 같은 0.2초라도 경계를 넘으면 10점, 안 넘으면 0점입니다.
4. **끼어듦 1개의 무게**: 18문항 중 1개가 끼어들면 평균이 약 5.6점(100/18) 깎입니다. 모든 문항이 한 계단씩 늦어지면 평균 10점이 깎입니다.

## 오늘 이렇게 쓰자 (제안)
1. 공식 키 점검 4단계(전체 1세션, `API_CHECK_1121.md`)에서 **판단 뒤 첫 소리 시간**(`first_audio_ms_rel - commit_ms_rel`)을 잽니다.
2. 그 값을 넣어 표를 다시 뽑습니다.
   `python -m team.scripts.eou_cost_table --pipeline <잰 값 p50>,<잰 값 p90> --out team/docs/EOU_COST_TABLE.md`
3. 공식 연습 음성이 나오면 같은 방식으로 규칙별 끼어듦을 재고 이 표에 넣습니다. **팀이 만든 음성의 쉼 길이(1.2·1.3·1.5초)는 우리가 정한 값**이라, 실제 고객의 쉼과 다를 수 있습니다.
4. Soniox 말 끝 모드(`AGENT_EOU_MODE=soniox_stream`)도 같은 표에 한 줄로 넣어 비교합니다.

## 한계
- 첫 소리 점수만 계산했습니다. 함수 문항의 공식 속도 점수는 (첫 소리 + 조회 뒤 답) 평균인데, 조회 뒤 답 시간은 말 끝 규칙과 상관없어 뺐습니다. 그래서 함수 문항에서는 실제 차이가 표의 절반 정도입니다.
- 끼어들면 속도만이 아니라 **사용자 경험(50점)**에도 나쁩니다(감점 사례에 "고객이 말하기 전에 답함"). 이 표는 속도만 봅니다. 비슷하면 끼어듦이 적은 쪽을 고르는 게 맞습니다.
- 측정은 대체물(삐 소리, 스크립트 LLM)이고 표본이 작습니다(18개, 24회). 순위가 뒤집히는 경계 근처는 실제 측정으로 다시 확인해야 합니다.
