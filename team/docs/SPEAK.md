# `speak()` 방식 검토

2026-11-19 · 정리 조여정 · 결론: **지금 방식(텍스트 스트리밍) 유지를 제안.** `speak()`로 바꿀 근거가 될 이점이 지금 구조에서는 작고, 지연·함수 점수 위험이 있음. 실제 키로 아래 '확인 실험'을 돌린 뒤 확정

## 두 방식
| | 지금 방식: 텍스트 스트리밍 | `speak()` 도구 방식 |
|---|---|---|
| 흐름 | LLM 텍스트 조각 → 문장 단위로 끊어 TTS (`dialog.py` `SentenceSplitter`) | LLM이 `speak({"text": "..."})` 도구 호출 → 서버가 인자를 꺼내 TTS |
| 대회 허용 | 기본 방식 | Q&A: "`speak()`를 Tool Call로 구현해도 됨" (필수 아님) |
| 팀 코드 변경 | 없음 | 도구 정의 추가, 도구 인자 스트리밍 처리, 함수 서버로 안 보내는 분기, 테스트 |

## 항목별 비교
| 항목 | 텍스트 스트리밍 | `speak()` | 근거 |
|---|---|---|---|
| **첫 소리** | 첫 문장이 완성되는 즉시 TTS | 도구 인자(JSON)를 조각마다 해석하면 비슷. **호출이 끝날 때까지 기다리면 답 전체를 만든 뒤에야 TTS** → 그만큼 늦어짐 | Chat Completions 스트리밍에서 도구 인자는 `{"text": "...` 형태 조각으로 옴. 부분 JSON 해석을 따로 만들어야 함 |
| **함수 점수** | 영향 없음 | **위험.** `speak`가 함수 서버(`tools_url`)로 나가면 운영진 중계에 "정의에 없는 함수 호출"로 기록됨. 반드시 서버 안에서 처리해야 함 | 채점: 호출하면 안 될 때 호출해도 틀림. 지금 `tools_client.py`는 정의에 없는 함수를 막지만, `speak`는 그보다 앞에서 따로 처리해야 함 |
| **조회 전에 결론 말하기** | 같은 위험 | 같은 위험 | 어느 방식이든 LLM이 결과를 받기 전에 "배송 중입니다"라고 쓸 수 있음. 막는 건 프롬프트·검사 규칙이지 방식이 아님 |
| **함수 호출 전 한마디** | 가능: 모델이 텍스트를 쓴 뒤 같은 응답에서 함수를 부르면, 지금 코드가 그 텍스트를 먼저 읽음 | 가능: `speak` + `get_order_info`를 한 응답에서 같이 호출 | 둘 다 LLM 첫 토큰(p50 약 1.15초, gpt-4.1)을 기다림. 미리 합성한 멘트(`feature/latency`의 `tool_ack`)는 0초 |
| **말할 것과 안 할 것 분리** | 모델이 메모·설명을 텍스트로 쓰면 그대로 읽힘 | 말할 문장만 `speak` 인자로 → 분리가 명확 | 지금 프롬프트에 "마크다운·괄호 설명 금지" 규칙이 있음 |
| **모델 호환** | 모든 Chat Completions 모델 | 모델이 `speak` 대신 그냥 텍스트를 쓰는 경우도 처리해야 함 (두 경로 모두 필요) | gpt-5.4-mini에서 도구 호출 형식은 실제 호출로 확인 필요 |
| **토큰·비용** | 최소 | 인자 JSON만큼 조금 더 | 크레딧 한정 (추가 지급 없음) |
| **구현·테스트 시간** | 0 | 부분 JSON 해석 + 분기 + 테스트 | 11/21 당일은 매뉴얼 반영이 우선 |

## 판단
- `speak()`의 실질적인 이점은 "말할 문장과 그 밖의 출력을 확실히 나눔" 하나입니다. 지금은 프롬프트 규칙으로 처리하고 있고, 이 때문에 생긴 문제 사례는 없습니다(`team/docs/ISSUES.md`).
- 대신 **함수 점수 위험**(speak가 중계로 새면 오답 호출)과 **첫 소리 지연 위험**(부분 JSON 해석을 안 하면 답 전체를 기다림)이 생깁니다.
- 함수 호출 전 대기 안내가 목적이라면 `speak()`가 아니어도 됩니다. 프롬프트로 "호출 전에 짧게 말하기"를 시키거나(LLM 첫 토큰만큼 대기), 미리 합성한 멘트를 쓰는 방법(대기 0초, 기본 꺼짐)이 있습니다.
